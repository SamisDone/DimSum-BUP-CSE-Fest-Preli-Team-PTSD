How it works

          

            

              
LLM Interpreter

              

                One call per request returns a structured entry for every note. Temperature
                zero, a fixed response schema, battery capacity supplied in the prompt so
                percentage reserves resolve to absolute kWh.
              

              

                Two normalisation rules decide most cases. Windows are start-inclusive and
                end-exclusive, so 1 PM to 3 PM is hours [13, 14]. And
                factor is the fraction that remains — an 80% reduction
                is 0.2, not 0.8.
              

              

                If the provider errors or stalls, the request is retried once, then falls
                through to a deterministic extractor. The model stays the primary path; the
                extractor exists so an outage degrades to a correct reading rather than
                silently dropping every directive.
              

            


            

              
Guardrail Validator

              

                Model output is untrusted until it passes deterministic checks. Anything
                unrepairable becomes no_op rather than reaching the optimizer as
                a bad constraint.
              

              
    
                
  • Exactly one entry per note, indexed 0…N−1, in order
    • 
                
  • Directive type must be one of the six supported values
    • 
                
  • Hours are unique integers 0–23, sorted ascending
    • 
                
  • Solar factor within 0 – 1 inclusive
    • 
                
  • Reserve finite, non-negative, never above capacity
    • 
                
  • Grid cap finite and non-negative
    • 
                
  • no_op ⟹ not applicable, adjustment null
    • 
                
  • Any other type ⟹ applicable, adjustment matches its shape
    • 
                
  • Demand, tariff and battery parameters can never be altered
    • 
              

              

                Try it above: edit a note into wording the model has not seen, or replace one
                with something irrelevant, and watch what comes back.
              

            


            

              
Math Optimizer

              

                A linear program solved with HiGHS. Continuous variables per hour for grid
                draw, solar used, charge and discharge.
              

              
minimize  Σ tariff[h] · grid[h]

s.t.  grid[h] + solar[h] + discharge[h] − charge[h] = demand[h]
      0 ≤ solar[h] ≤ effective_solar[h]
      0 ≤ charge[h] ≤ max_charge        (0 in no-charge hours)
      0 ≤ discharge[h] ≤ max_discharge  (0 in no-discharge hours)
      0 ≤ grid[h] ≤ cap[h]              (where a cap applies)
      reserve[h] ≤ E[h] ≤ capacity
      E[23] = E[0]

              

                Curtailment is allowed — unused solar is simply not taken. Totals are derived
                from the rounded hourly plan, never from solver internals, because the plan is
                the source of truth.
              

            


            

              
Final Validator

              

                Not yet implemented. This stage is a stub in the service, so the page does not
                claim any plan has been independently re-checked.
              

              
    
                
  • —24 unique hours, 0 through 23
    • 
                
  • —Energy balance holds every hour
    • 
                
  • —Solar used never exceeds effective solar
    • 
                
  • —Battery bounds and hourly rate limits
    • 
                
  • —Charge and discharge windows respected
    • 
                
  • —Grid caps respected
    • 
                
  • —Final battery energy equals the initial level
    • 
                
  • —Totals recomputed from the hourly plan

The API

          

            This console is a client of the same public endpoints a judge would call. It adds
            no authentication and no gate — the service answers directly.
          

          
GET  /health            → 200 {"status":"ok"}
POST /optimize-energy   → 200 scenario_id, directive_interpretation, hourly_plan,
                              total_grid_kwh, total_cost_bdt, peak_grid_kwh, plan_summary
GET  /api-info          → service description
